# ADR 0002: Source/server identity (Jellyfin-first)

- Status: Accepted
- Type: Product
- Date: 2026-11-08
- Owners: TBD
- GitHub: #15
- Affects: REQ-ACS-01, REQ-LIB-01/03/04, future multi-source/merge behavior

## Context

Build 1 connects one Jellyfin server. The system needs a stable identity for a source/server so configuration, linked access, sync state, availability, and future merge/provenance do not depend on free-form user input or fragile URL strings.

## Constraints

- Deterministic and not user-invented.
- Stable across routine config edits where the underlying source is the same.
- Handles URL normalization (scheme, host case, default ports, trailing slash) without guessing dangerously.
- Does not treat obviously different endpoints as the same source without evidence.
- Does not leak credentials; secrets are never part of identity.
- Build 1 only needs a good Jellyfin-first solution; it must not block future multi-source identity.

## Decision

Accept **Option A for Build 1 (Jellyfin-first): verified server identity + opaque internal ID + normalized endpoint mapping**.

Accept **Option B as a future fallback/capability**, not the primary identity mechanism: normalized URL-derived identity may be used only when a source cannot provide a reliable verified identity signal, and only with explicit rules recorded in a follow-up ADR/connector contract. It must not silently replace verified identity.

### Identity model

- Each source connection has an **opaque internal ID** generated by the system.
- For Jellyfin, add/verify fetches **server identity information** from the Jellyfin API and uses it as the primary basis for stable identity and deduplication.
- The **base URL** is stored as connection configuration, normalized for comparison/display (no credentials/query fragments; normalization rules documented). It is not the canonical identity when verified identity exists.
- A **human label** is separate from identity (e.g. Jellyfin server name, editable display label later).

### Duplicate handling — depends on deployment/access model

The duplicate-resolution UX must not leak information across users in deployments where users can add their own sources/connections.

**Build 1 / household or operator-managed setup:** if the same verified Jellyfin server is added again, detect the duplicate and offer a clear resolution path: **use existing source**, **update endpoint/config**, or **cancel**. Do not silently create a conflicting identity.

**Future public or multi-user self-add setup (slots/connections added by different users):** do not reveal that another user already connected the same server. Deduplication/visibility rules must be scoped to the actor’s permissions and trust boundary (for example, deduplicate within the same owner/admin scope; treat cross-user visibility as a separate privacy/security decision). This requires a follow-up ADR before implementing public/user-added source connections.

### Fallback when verification is unavailable

Build 1 should fail clearly with an actionable message if server identity cannot be verified. A future B-style fallback may be allowed only by explicit connector/policy decision, with warnings about alias/move/duplicate risks.

## Options considered

1. **A. Verified server identity + normalized endpoint mapping (accepted for Build 1)** — stable, not user-invented; tolerant of endpoint presentation differences; requires verified identity signal.
2. **B. Normalized URL hash/ID (future fallback only)** — simple; fails for aliases/moves/reverse proxies; not primary identity.
3. **C. Operator-assigned internal ID** — explicit but drifts and puts identity burden on users/admins.
4. **D. Random internal ID only** — stable once created; needs extra rules for duplicate detection/re-adding.

## Consequences

- Build 1 has a stable Jellyfin source identity without user-chosen IDs.
- Duplicate handling is intentionally stricter about privacy in future multi-user/public modes.
- Connector-specific identity strategies may be needed later; this ADR sets the baseline rules.

## Follow-up

- Implement Jellyfin verification during add/refresh flow.
- Document URL normalization rules and human label behavior.
- Open follow-up ADR for public/multi-user self-add deduplication/visibility before implementing that mode.
- Open follow-up connector/policy decision if a verified identity source is unavailable.

## Outcome

**Accepted** (A now, B as future fallback) — verified Jellyfin server identity + opaque internal ID + normalized endpoint mapping for Build 1; duplicate handling scoped by deployment model (household/operator vs future public/multi-user).
